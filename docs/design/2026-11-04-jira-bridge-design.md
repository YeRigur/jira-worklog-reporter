# Jira bridge: export straight from Jira, without JQL and CSV

Date: 2026-11-04 · Status: approved design, not implemented

## Problem

Today the page needs a Jira CSV export: copy the JQL, paste it into Jira's
search, choose *Export → CSV (all fields)*, upload the file. In practice this
fails in several ways:

- Jira's JQL rejects or mis-resolves `worklogAuthor in ("email", …)` — emails
  are often hidden on Jira Cloud, so the query errors or finds the wrong issues.
- The export sometimes contains only the issues of the current page, and a CSV
  is capped at 1000 issues, so longer periods need one export per month.
- Not everyone can open the team's saved filter.
- The whole process is many manual steps.

## Goal

The person loads the settings file, ticks people, checks the Jira site, clicks
**Start**. The page gets the data from Jira's REST API and builds the same
Excel as today. The page stays a static GitHub Pages site and still makes no
network connection of its own.

Non-goals: a backend or proxy, API tokens, a browser extension, changing
`src/vendor/worklogs-export.js`.

## Why a bookmarklet bridge

A static page on `github.io` cannot call `https://<site>.atlassian.net/rest/…`:
Jira Cloud sends no CORS headers for other origins, with cookies or with an API
token. Code running *inside* a Jira tab is same-origin and uses the person's
session. Jira Cloud sends no `Cross-Origin-Opener-Policy` (checked 2026-11-04
on public Cloud sites: only `x-frame-options: SAMEORIGIN`), so a tab the page
opens with `window.open` keeps `window.opener`, and the two can talk with
`postMessage`. Chrome and Firefox do not apply the page's CSP to bookmarklets.

`runWorklogsExport(fetch, location)` already takes `fetch` as a parameter and
speaks Jira REST (`POST /rest/api/3/search/jql`, `GET /rest/api/3/issue/{key}/worklog`).
Today the page hands it an emulator over the CSV. The bridge hands it a fetch
that runs in the Jira tab instead. The export logic — JQL by accountId,
paging, worklog fetching, sheets — stays the extension's code, unchanged.

Rejected: a "collector" bookmarklet that downloads everything itself and
returns one JSON (duplicates the extension's query logic, large bookmarklet to
keep in sync); a proxy server (data and token leave the browser).

## 1. Flow and settings

### Settings file (`worklogs-settings.json`), backward compatible

- `site` (new): e.g. `"acme.atlassian.net"`. Prefills the site field.
- `roster` (unchanged): the team's emails — the people to pick from.
- `accounts` (new): `{ "email": "accountId" }`. A cache the page fills by
  itself; nobody edits it by hand. `mergeSettings`: newer file wins per email.

Unknown fields are ignored as today. A file without `site`/`accounts` works.

### Start screen (Jira mode is the default)

1. **Period** — the two dates and *Last month*, as today. The month split and
   *Copy JQL* go away from this mode (no 1000-issue cap).
2. **People** — a checklist of the roster, with *All* / *None*, and an *Add
   email* field. An added email goes into the stored settings (browser) and
   into the file on *Save settings file*. The checked set is remembered in the
   browser.
3. **Jira site** — text field, prefilled from `settings.site`.
4. **Start** button.
5. A collapsed link *Or upload a CSV* reveals today's CSV path, unchanged.

### After Start

1. The page opens `https://<site>/jira/your-work` in a new tab and shows:
   "In the Jira tab, click the *Worklogs bridge* bookmark."
2. First time only: a draggable *Worklogs bridge* link with a short "drag it to
   your bookmarks bar" note, and *Show code*.
3. The person clicks the bookmark in the Jira tab → the page shows
   "Connected to acme.atlassian.net".
4. The page resolves accountIds for checked emails missing from `accounts`
   (see §3). People not found are listed; the run continues without them.
5. The extension's export runs through the bridge; its progress messages show
   on the page.
6. Preview and Download work as today. The Jira tab may be closed afterwards.

## 2. The bridge

### Bookmarklet (`src/core/bridge.js`)

Generated by the page as a `javascript:` URL with the page's own origin baked
in as `PAGE_ORIGIN` (`location.origin`: the GitHub Pages origin in production,
`http://localhost:8000` locally). Protocol version `v: 1`. When clicked in the
Jira tab:

1. If `window.opener` is missing: `alert('Open Jira with Start on the export page, then click this bookmark there.')` and stop.
2. Post `{ type: 'wl-bridge:ready', v: 1, site: location.host }` to
   `window.opener` with target origin `PAGE_ORIGIN`.
3. Listen for `{ type: 'wl-bridge:fetch', id, method, path, body }`. Accept a
   message only when `event.origin === PAGE_ORIGIN` and
   `event.source === window.opener`; ignore everything else silently.
4. Check the request against the allow-list (below). Allowed → `fetch(path,
   { method, body, credentials: 'include', headers: { Accept: 'application/json',
   'Content-Type': 'application/json' when there is a body } })`, then post
   `{ type: 'wl-bridge:response', id, status, body: text, retryAfter }`.
   Refused → `status: 403`, body `"Refused by the bridge"`. Network error →
   `status: 0`, body = the error message.
5. Show a small fixed badge in the Jira tab: "Worklogs bridge · connected ·
   N requests".
6. Clicking it again does not install a second listener; it re-sends `ready`.

### Allow-list (read-only)

| Method | Path |
|---|---|
| POST | `/rest/api/3/search/jql` |
| GET | `/rest/api/3/issue/{key}/worklog` (query allowed) |
| GET | `/rest/api/3/user/search` (query allowed) |
| GET | `/rest/api/3/user` (query allowed) |
| GET | `/rest/api/3/myself` |

`path` must start with a single `/`, contain no `//`, no `..`, no scheme, and
no `#`. Anything else is refused. The same check is exported for tests and is
the source the bookmarklet text is built from, so they cannot drift.

### Page side (`src/app/bridge-client.js`)

- `openJira(site)` → `window.open(url, 'jira-worklogs-bridge')`. Returns null
  when the popup is blocked.
- `waitForBridge(win, site)` resolves on `ready` with
  `event.origin === 'https://' + site` and `event.source === win`; rejects on
  version mismatch (`v` lower than expected) with an *update the bookmark*
  error.
- `createBridgeFetch(win, site)` → a `fetch(url, init)` that posts a request
  with a fresh id and resolves to `new Response(body, { status })`. Per-request
  timeout 60 s. On 429, waits `Retry-After` (or 2 s, 4 s, 8 s) and retries up
  to 3 times.
- Polls `win.closed` every second; on close, rejects every pending request
  with "The Jira tab was closed."
- The page's CSP stays `connect-src 'none'`: `postMessage` is not a network
  connection.

## 3. Page integration

- `state.source: 'jira' | 'csv'`. The CSV path (`dataset`, emulator, column
  and author pages) is untouched.
- **Account lookup** (`src/core/accounts.js`): for each checked email without
  `accounts[email]`, `GET /rest/api/3/user/search?query=<email>`. Pick the
  result whose `emailAddress` equals the email (case-insensitive); else, when
  exactly one result comes back and its email is hidden, take it and mark it
  "found by search"; else not found. Found ids are saved to
  `settings.accounts` through the settings store.
- **Export config** (`buildJiraExportConfig` in `src/core/export-config.js`):
  `users` = accountIds of the checked people; `_userMetadata` =
  `{ accountId: { displayName, email } }` from the lookup; `_teamEmails` =
  checked emails; `_roster`, `_assignments`, `_groupByDomain`,
  `_projectsGroups`, sheets and labels as today; `exportFields` from the
  catalog's column template, every catalog field treated as available (the API
  returns any field). No hand-made column bindings in this mode.
- **Response cache** (`src/core/fetch-cache.js`): wraps the bridge fetch; key
  = method + path + body; only 2xx responses are kept. The first Preview goes
  to Jira and shows progress; Summary toggles and Download replay from the
  cache. The cache is cleared when period, people or site change. After a
  closed tab, Start again re-requests only what is missing.
- **Signature** (what triggers a rebuild) in Jira mode: source, site, period,
  checked accountIds, summary toggle, settings revision.
- **Projects without a group**: still shown, from the projects in the cached
  search responses (`fields.project`).
- **`?demo`**: a fake bridge backed by the existing emulator and demo data, so
  the Jira flow can be stepped through without Jira.

## Errors

| Situation | What the person sees |
|---|---|
| Popup blocked | "Allow pop-ups for this page" + Retry |
| No `ready` within 2 min | "Click the *Worklogs bridge* bookmark in the Jira tab" + link to the CSV path (keeps waiting) |
| 401/403 from Jira | "Sign in to Jira in that tab, then click the bookmark again" |
| 429 | Retried automatically (see above); after 3 tries, the export's own error |
| Jira tab closed mid-run | "The Jira tab was closed" + Start again (cache kept) |
| Old bookmark version | "Update the bookmark" + the draggable link |
| Nobody checked | Start disabled, "Pick at least one person" |
| Some emails not found | Listed under People; run continues |

## Testing (`node --test`)

- `tests/bridge.test.js`: allow-list accepts the five calls and refuses `//evil.com/x`,
  `/rest/api/3/../x`, `https://…`, `DELETE`, `PUT`, other paths; the generated
  bookmarklet parses as JS (`new Function`) and contains the given origin.
- `tests/bridge-client.test.js`: fake window pair — wrong origin/source ignored,
  version mismatch, timeout, closed tab rejects pending, 429 retry.
- `tests/fetch-cache.test.js`: hit, miss, non-2xx not cached, clear.
- `tests/accounts.test.js`: exact match, hidden email single result, not found,
  several candidates.
- End to end: `runWorklogsExport` over the cache + fake bridge + emulator on the
  existing fixtures produces the same sheets as the CSV path on the same data.
- Manual: `?demo` locally. A live Jira run is done by the user (needs their
  sign-in).
